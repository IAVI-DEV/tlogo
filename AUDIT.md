# tlogo Repository Audit

**Date:** 2026-02-28
**Scope:** Full codebase review — code quality, correctness, tests, CI/CD, packaging, security

---

## Repository Overview

**tlogo** is a sequence logo generator for aligned FASTA files with HxB2 coordinate mapping for HIV Env gp160 protein. It provides a CLI (`click`) with three commands:

- `tlogo logo` — Standard logo plot at selected HxB2 positions
- `tlogo window` — Per-animal window logo at a focused position +/- radius
- `tlogo auto` — Auto-detect variant positions and generate window logos

**Structure:** Well-organized `src/` layout with 7 modules, 5 test files, 2 CI workflows, and an example FASTA alignment. Dependencies: click, biopython, matplotlib, logomaker, pandas.

## Bugs

### 1. No-op expression in `matrix.py:191` (and `window.py:47`)

```python
to_type = matrix_type if matrix_type != "counts" else "counts"
```

This expression **always** evaluates to `matrix_type` — it's a no-op. If `matrix_type == "counts"`, it returns `"counts"`. Otherwise it returns `matrix_type`. The variable `to_type` is always identical to `matrix_type`. This appears to be a copy-paste error where the original intent was likely to map `"counts"` to a different logomaker type (e.g., `"counts"` vs `"weight"`).

**Files:** `src/tlogo/matrix.py:191`, `src/tlogo/window.py:47`

### 2. `_version.py` tracked in version control despite header warning

`src/tlogo/_version.py` contains the comment `"don't change, don't track in version control"` (auto-generated by setuptools-scm), yet it is committed. This file should be added to `.gitignore` since `setuptools_scm` regenerates it during builds. Tracking it causes unnecessary diff noise on every version bump.

**File:** `src/tlogo/_version.py`

### 3. No alignment length validation in `parse_alignment`

`io.py:parse_alignment` reads FASTA sequences into a dict but never validates that all sequences have equal length. If unaligned sequences are provided, downstream code (e.g., `compute_gap_fraction`, `find_variant_positions`, `build_logo_matrix`) will silently produce wrong results or crash with `IndexError` when indexing columns.

**File:** `src/tlogo/io.py:11-23`

### 4. Missing encoding parameter in `read_selection_tsv`

```python
with open(tsv_path) as f:
```

Uses the platform's default encoding rather than explicit `encoding="utf-8"`. On Windows systems with non-UTF-8 locale, this could fail or produce garbled data.

**File:** `src/tlogo/matrix.py:101`

## Code Quality Issues

### 5. Cross-module private function imports

`window.py` imports private functions from `logo.py`:

```python
from tlogo.logo import _save_figure, _y_axis_label, apply_nature_style
```

`_save_figure` and `_y_axis_label` are prefixed with `_` indicating they're module-private, but they're consumed across module boundaries. These should either be renamed without the underscore (making them part of the public API) or extracted to a shared utility module.

**File:** `src/tlogo/window.py:22`

### 6. Significant code duplication between `render_logo_plot` and `render_window_logo`

Both functions share nearly identical logomaker setup, spine styling, tick configuration, and axis formatting. The shared logic could be extracted into a helper, reducing the ~50 lines of duplication.

**Files:** `src/tlogo/logo.py:82-189`, `src/tlogo/window.py:26-107`

### 7. No `IndexError` guard in column-access code

Multiple functions index into sequences by column without bounds checking:

- `compute_gap_fraction(sequences, col)` — `seq[col]`
- `find_variant_positions` — `s[col]`
- `resolve_window_cols` — `compute_gap_fraction(sample_seqs, col)`

While alignment sequences *should* be equal length, the lack of any validation (see Bug #3) means these can crash on malformed input with unhelpful `IndexError` tracebacks.

**Files:** `src/tlogo/matrix.py:140`, `src/tlogo/matrix.py:241`

## Test Coverage Gaps

### 8. No tests for `logo.py` rendering functions

`render_logo_plot` and `process_standard_logo` are only tested indirectly via CLI smoke tests. Direct unit tests would catch rendering regressions faster.

### 9. No tests for `window.py` rendering functions

Same as above — `render_window_logo`, `process_window_mode`, `process_auto_variants` lack direct unit tests.

### 10. No execution test for `tlogo auto` command

`test_cli.py` only tests `auto --help`. Unlike `logo` and `window`, there's no test that actually *runs* the auto command with input data.

### 11. No test for `read_selection_tsv`

The TSV parser in `matrix.py:94-129` has no dedicated test. Edge cases (missing columns, non-numeric p-values, empty hxb2 fields) are untested.

### 12. No test for `build_logo_matrix`

The core matrix-building function at `matrix.py:168-200` is untested directly.

## CI/CD Issues

### 13. `publish.yml` uses `if: always()` anti-pattern

```yaml
if: always() && needs.build.result == 'success'
```

The `always()` modifier causes the job to be evaluated even when the workflow is **cancelled**. Since the condition also checks `needs.build.result == 'success'`, a cancelled workflow won't actually publish, but this pattern is a well-known anti-pattern that can cause unexpected behavior. It should be:

```yaml
if: needs.build.result == 'success'
```

Or simply remove the `if:` entirely, since `needs: [build]` already enforces that the build must succeed.

**File:** `.github/workflows/publish.yml:45`

### 14. No linting or type-checking in CI

The CI pipeline runs tests but has no static analysis step. Adding `ruff` (or `flake8`) and `mypy` would catch issues like the no-op expression (Bug #1) automatically.

### 15. No test coverage reporting

There's no `pytest-cov` or coverage reporting. This makes it difficult to identify untested code paths.

### 16. Python 3.14 in classifiers but not in CI matrix

`pyproject.toml` lists `Programming Language :: Python :: 3.14` in classifiers, but CI only tests 3.9 and 3.13. Python 3.14 is still in development and may have breaking changes.

**Files:** `pyproject.toml:26`, `.github/workflows/ci.yml:14-15`

## Security

No security vulnerabilities found. The codebase:

- Performs no network calls
- Has no `eval`/`exec`/`pickle` usage
- Uses `csv.DictReader` safely for TSV parsing
- Constrains file operations to user-specified paths
- `.gitignore` properly excludes `.env`, `.envrc`, secrets

The only minor concern is Bug #4 (missing encoding parameter), which is a portability issue rather than a security risk.

## Project Configuration

### Positive

- Proper `src/` layout with `setuptools-scm` version management
- Comprehensive `.gitignore`
- MIT license
- Clear README with install, usage, dev, and release instructions
- Trusted publishing (OIDC) for PyPI — no API tokens in CI
- Cross-platform CI matrix (Ubuntu, macOS, Windows)
- Hypothesis property-based testing in the test suite

### Suggestions

- Add `src/tlogo/_version.py` to `.gitignore`
- Consider adding a `py.typed` marker for downstream type-checking
- Consider adding `ruff` configuration to `pyproject.toml`
- Consider pinning GitHub Actions to SHA digests for supply-chain safety (e.g., `actions/checkout@<sha>` instead of `@v4`)
